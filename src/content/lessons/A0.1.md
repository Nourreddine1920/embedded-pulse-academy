## Learning objectives

By the end of this lesson you will be able to:

1. **State** the size and signedness of every standard integer type on `arm-none-eabi-gcc`, including the three that surprise people: plain `char` is **unsigned**, `int32_t` is **`long`**, and `enum`s are **as small as possible**.
2. **Choose** the right `<stdint.h>` type for a hardware register, a sensor sample, a timestamp, a loop index and a byte buffer, and justify each choice.
3. **Predict** the type and value of any expression that mixes `uint8_t`, `uint16_t`, `int`, `int32_t` and `uint32_t` operands, by applying *integer promotion* and the *usual arithmetic conversions*.
4. **Find and fix** the seven classic promotion bugs (listed in the cheat sheet), in code and in disassembly.
5. **Catch** these bugs automatically with `-Wextra -Wconversion`, `_Generic`, `_Static_assert` and the on-target trap sanitizer `-fsanitize=undefined -fsanitize-undefined-trap-on-error`.
6. **Print** fixed-width values portably with `<inttypes.h>` (`PRIu32`, `PRIX32`, `PRId16`…).

## Why this matters

Picture a battery-management board in an e-bike. Every 100 ms it reads each cell's temperature from a digital sensor over I2C. The sensor returns a **signed 16-bit** value in two bytes, at 0.01 °C per LSB (LSB = *least significant bit*, one step of the value).

In the summer lab tests everything works. In the first winter field test, at −2 °C, the firmware logs **+653.36 °C** and trips the over-temperature cutoff. The rider is stranded. The cause was one line:

```c
int32_t raw = (msb << 8) | lsb;   /* 0xFF, 0x38 -> +65336, not -200 */
```

Nothing is wrong with the sensor, the I2C driver or the maths. The **type** of one expression is wrong. The same class of bug shows up again and again in industry:

- **Ariane 5, flight 501 (1996).** A 64-bit floating-point value was converted to a 16-bit signed integer. The value didn't fit, the conversion raised an unhandled exception, and both inertial reference units shut down. The rocket was lost about 40 s after lift-off.
- **Boeing 787 generator control units (2015).** An FAA airworthiness directive required periodic power cycling, because after **248 days** of continuous power the units could shut down. The widely reported cause: a 32-bit signed counter of hundredths of a second overflows after 2³¹ / 100 s ≈ 248.5 days.
- **Every STM32 timer driver you will write** (A7.4, A7.6) computes `now - start` on a 16-bit counter that wraps every 65 536 ticks. Written the obvious way, it's wrong.

This lesson is the foundation for everything that follows: register masks (A0.2), register access (A0.4), baud-rate maths (A8.2), ring-buffer indices (A8.4), sensor decoding (A10.6), ADC scaling (A11.5), CRC (A14.5), and tick arithmetic in FreeRTOS (B3.3).

## Concept explanation

````layer beginner
### What is an integer type, really?

Inside the microcontroller (MCU) a number is a row of **bits**, each 0 or 1. An integer *type* tells the compiler two things:

1. **How many bits** the variable has (its *width*): 8, 16, 32 or 64.
2. **How to read those bits**: *unsigned* (never negative) or *signed* (can be negative).

```callout analogy title="Analogy: the odometer"
An **unsigned** 8-bit variable is like a car odometer with 3 digits that can only show 000–255. Drive one more kilometre at 255 and it rolls over to **000**. It never shows a negative value, and it never "overflows" into a 4th digit. It just wraps.

A **signed** variable is the same odometer, but we agree that the top half of the dial (128–255) *means* −128 to −1. Same bits, different meaning.
```

The signed format used by every modern CPU is called **two's complement**. For N bits, a negative number −x is stored as the unsigned number 2ᴺ − x. In 8 bits:

| Bits | Read as unsigned (`uint8_t`) | Read as signed (`int8_t`) |
|---|---|---|
| `0000 0001` | 1 | 1 |
| `0111 1111` | 127 | 127 |
| `1000 0000` | 128 | **−128** |
| `1111 1111` | 255 | **−1** |

The leftmost bit is the **MSB** (*most significant bit*). In a signed type it acts as the **sign bit**: 1 means negative.

### Why not just use `int`?

The C standard only says `int` is *at least* 16 bits. It is 16 bits on an 8-bit AVR (Arduino Uno) and 32 bits on ARM Cortex-M. Firmware talks to hardware with exact sizes: an STM32 register is exactly 32 bits, a sensor sample exactly 16 bits, a UART byte exactly 8 bits. So we use the **fixed-width types** from `<stdint.h>`, which say their size in their name:

| Type | Bits | Range |
|---|---|---|
| `uint8_t` | 8 | 0 … 255 |
| `int8_t` | 8 | −128 … 127 |
| `uint16_t` | 16 | 0 … 65 535 |
| `int16_t` | 16 | −32 768 … 32 767 |
| `uint32_t` | 32 | 0 … 4 294 967 295 |
| `int32_t` | 32 | −2 147 483 648 … 2 147 483 647 |
| `uint64_t` / `int64_t` | 64 | 0 … 1.8×10¹⁹ / ±9.2×10¹⁸ |

### The rule that causes most bugs: integer promotion

Here is the single most important sentence in this lesson:

> **C never does arithmetic on types smaller than `int`.** Before `+ - * / % ~ << >> & | ^` or a comparison, every `char`, `uint8_t`, `int8_t`, `uint16_t` and `int16_t` operand is first converted ("promoted") to `int`, which is 32 bits on ARM.

```callout analogy title="Analogy: the 32-digit calculator"
Imagine a calculator whose display always has 32 digits. You can type a small 8-bit number, but the calculator copies it into its 32-digit display first, pads it with zeros, and only then computes. The answer comes out 32 digits wide. If you wanted an 8-bit answer, *you* have to cut it back to 8 digits.
```

Most of the time you never notice. Here is the classic case where you do. Step through it:

```anim
promotion-complement
```

You now know the core idea. The next two layers explain exactly *when* conversions happen, and what the CPU and compiler do with them.
````

````layer intermediate
```c

uint32_t id = 0x80010203UL;
printf("t=%" PRId32 " id=0x%08" PRIX32 "\r\n", t, id);
/* expands to "t=%ld id=0x%08lX\r\n" on arm-none-eabi */
```

### Choosing the right type

| What you're storing | Use | Why |
|---|---|---|
| A peripheral register value or mask | `uint32_t` | Registers are 32-bit; masks must be unsigned (A0.2) |
| Raw bytes from UART/SPI/I2C, buffers | `uint8_t` | Exactly one byte, no sign surprises |
| A signed sensor sample (temperature, accel) | `int16_t` / `int32_t` | Matches the datasheet's two's complement format |
| Timestamps, tick counts, cycle counts | `uint32_t` | Wrap-around subtraction is well defined for unsigned types |
| Loop indices, array sizes, `memcpy` lengths | `uint32_t` or `size_t` | Native width: no extra instructions, no 255 limit |
| Yes/no flags | `bool` | Converts any non-zero to `1` (see mistake #6) |
| Text | `char` | Only for characters, never for small numbers |
| Local arithmetic temporaries | `int32_t` / `uint32_t` | That's the width the CPU computes in anyway |

### Integer promotion: the exact rule

> **C11 §6.3.1.1 ¶2**: if an `int` can represent all values of the original type, the value is converted to `int`; otherwise to `unsigned int`.

On ARM, `int` is 32 bits, so `uint8_t`, `int8_t`, `uint16_t`, `int16_t`, `char`, `short`, `bool` and small enums all become **signed `int`**. That includes the *unsigned* small types.

Promotion is applied to the operands of:

- arithmetic: `+ - * / %`
- bitwise and shift: `~ & | ^ << >>`
- comparison: `< <= > >= == !=`
- unary `+` and `-`, and the controlling expression of `switch`
- **arguments passed through `...`**, which is why you can print a `uint8_t` with `%u`: it arrives as `int` (*default argument promotions*).

Promotion is **not** applied to assignment. Assigning a 32-bit result to a `uint8_t` truncates it back to 8 bits (modulo 256).

### The usual arithmetic conversions

After promotion, if the two operands of a binary operator still have **different types**, C converts them to a common type using these steps (C11 §6.3.1.8):

```mermaid caption="The usual arithmetic conversions for integer operands (after promotion)"
flowchart TD
    A["Both operands promoted<br/>(uint8_t, int16_t, char... become int)"] --> B{"Same type now?"}
    B -- yes --> Z["Compute in that type"]
    B -- no --> C{"Same signedness?"}
    C -- yes --> D["Convert the lower-rank one<br/>to the higher-rank type"]
    C -- no --> E{"Unsigned operand has<br/>rank greater than or equal to the signed one?"}
    E -- yes --> F["Signed operand becomes UNSIGNED<br/>(the dangerous case)"]
    E -- no --> G{"Signed type can hold<br/>every value of the unsigned one?"}
    G -- yes --> H["Unsigned operand becomes the signed type"]
    G -- no --> I["Both become the unsigned version<br/>of the signed type"]
    D --> Z
    F --> Z
    H --> Z
    I --> Z
```

*Rank* is basically size order: `long long` > `long` > `int` > `short` > `char`. On ARM, the case that bites is the red one. **`int` vs `unsigned int`** and **`int32_t` vs `uint32_t`** have equal rank, so the signed side becomes unsigned, and a negative value becomes a huge positive one:

```anim
signed-unsigned-compare
```

### Worked examples (all verified on GCC 10.3, Cortex-M4)

| Expression | Type after conversions | Value |
|---|---|---|
| `(uint8_t)200 + (uint8_t)100` | `int` | 300 (no wrap: computed in 32 bits) |
| `(uint8_t)(200 + 100)` | `uint8_t` | 44 (300 mod 256) |
| `(uint16_t)65535 * (uint16_t)65535` | `int` | **undefined behaviour** (overflows `int`) |
| `(uint32_t)65535 * 65535` | `unsigned long` | 4 294 836 225 |
| `-1 < 1U` | `int` (the result) | **0**: `-1` became `4294967295U` |
| `(int32_t)-1 < (uint32_t)1` | `int` | **0**: same rank, signed side becomes unsigned |
| `(int16_t)-1 < (uint16_t)1` | `int` | **1**: both promote to `int` first, so it's safe |
| `0xFFFFFFFF` | `unsigned int` | hex literals may become unsigned |
| `4294967295` | `long long` | decimal literals never become unsigned |
| `1 << 31` | `int` | **undefined behaviour**: use `1UL << 31` |

The row with `(int16_t)-1 < (uint16_t)1` is worth a second look. Small types are *safer* to mix than 32-bit ones, because promotion makes both sides `int` before the dangerous rule can apply.

### Timers wrap. Your arithmetic must too.

STM32 timers TIM3/TIM4 (and many sensors' counters) are 16-bit. Measuring elapsed time is `now - start`. But both operands are promoted to `int`, so the subtraction **doesn't wrap**. Drag the sliders, or press *Run the clock*:

```anim
wrap-wheel
```

The rule: **do tick arithmetic in the counter's own unsigned width**, `(uint16_t)(now - start)`. For 32-bit counters (`HAL_GetTick()`, `DWT->CYCCNT`, the FreeRTOS tick) plain `uint32_t` subtraction already wraps correctly, because `uint32_t` operands are not promoted.

### Integer constants and their suffixes

A literal's type is chosen *before* the expression is evaluated (C11 §6.4.4.1). The first type from the list that can hold the value wins:

| Literal form | Candidate types in order |
|---|---|
| Decimal, no suffix: `100`, `4294967295` | `int`, `long`, `long long` (never unsigned) |
| Hex/octal, no suffix: `0xFF`, `0xFFFFFFFF` | `int`, `unsigned int`, `long`, `unsigned long`, … |
| `U` suffix: `100U` | `unsigned int`, `unsigned long`, … |
| `UL` suffix: `1UL` | `unsigned long`, `unsigned long long` |

That's why ST's CMSIS headers write every mask as `(0x1UL << 13U)`: the constant is `unsigned long` **before** the shift, so shifting into bit 31 is well defined.

### Reading the documentation

- **C11 standard** (free final draft *N1570*): §6.3.1.1 *Boolean, characters, and integers* (promotion), §6.3.1.3 *Signed and unsigned integers* (conversion), §6.3.1.8 *Usual arithmetic conversions*, §6.5.7 *Bitwise shift operators*, §7.20 `<stdint.h>`, §7.8 `<inttypes.h>`.
- **GCC manual** → *C Implementation-Defined Behavior* → *Integers*: documents that out-of-range conversion to a signed type is done modulo 2ᴺ, and that `>>` on a negative value is arithmetic (sign-filling).
- **AAPCS32** (Arm IHI 0042) → *Arithmetic Types* / *Fundamental Data Types*: the sizes table above, plain `char` = unsigned, enum sizing.
````

````layer advanced
### What the CPU actually executes

The Cortex-M4 has **no 8-bit or 16-bit arithmetic**. All 13 general registers and the ALU are 32 bits wide, so promotion costs nothing: it happens for free when the value is **loaded**.

| Operation | Instruction | Effect |
|---|---|---|
| Load `uint8_t` / `uint16_t` | `LDRB` / `LDRH` | Zero-extends into a 32-bit register |
| Load `int8_t` / `int16_t` | `LDRSB` / `LDRSH` | Sign-extends into a 32-bit register |
| Store 8/16 bits | `STRB` / `STRH` | Stores the low bits (truncation is free) |
| Re-truncate a register | `UXTB` / `UXTH` | Zero-extend low byte/half-word in place |
| Re-sign-extend a register | `SXTB` / `SXTH` | Sign-extend low byte/half-word in place |
| Compare | `CMP` then a condition | **Signed**: `GE LT GT LE` (use N, V flags). **Unsigned**: `HS/CS LO/CC HI LS` (use C, Z flags) |

So the *signedness* of a comparison isn't in the data. It's the condition code the compiler picks. For `(int32_t)-1 < (uint32_t)1`, GCC emits `CMP r0, r1` followed by an **unsigned** `ITE CS` sequence. You can see the promotion bug directly in the disassembly.

### The hidden cost of small loop counters

Promotion is free on load, but **wrapping back to 8 bits is not**. If a `uint8_t` lives in a register and is incremented, the compiler must emit `UXTB` after every `+1` to keep the value's modulo-256 behaviour. Here is the lab's loop, compiled with GCC 10.3 at `-O2`, length unknown at compile time:

```armasm title="sum_with_u32_index — 4 instructions per iteration"
36:  ldrb.w  r2, [r3], #1     ; load data[i], pointer++
3a:  cmp     r3, r1
3c:  add     r0, r2           ; sum += data[i]
3e:  bne.n   36
```

```armasm title="sum_with_u8_index — 8 instructions per iteration"
56:  add     r2, r4           ; address = base + i
58:  adds    r3, #1           ; i + 1 ...
5a:  ldrb    r2, [r2, #4]
5c:  uxtb    r3, r3           ; ... truncated to 8 bits (i = i mod 256)
5e:  cmp     r3, r1
60:  add     r0, r2
62:  mov     r2, r3
64:  bcc.n   56
```

Three findings from the real compiler output, which you'll reproduce in the lab:

1. At **`-O0`** (CubeIDE's *Debug* default) both loops compile to the **same** 15-instruction body, because every variable lives on the stack and `STRB` truncates for free.
2. At **`-O2`** with a **runtime** length, the `uint8_t` loop is 8 instructions vs 4: the `UXTB` blocks the pointer-increment optimisation.
3. At **`-O2`** with a **constant** length ≤ 255, GCC *proves* `i` can't wrap and emits **identical** code for both.

Conclusion: never use `uint8_t` "to save memory" for locals. A local lives in a 32-bit register anyway. Use `uint32_t`, `size_t` or `uint_fast8_t` (which *is* 32-bit here).

### Undefined vs implementation-defined: why "it works in Debug" means nothing

The C standard has three levels of "not fully specified", and they behave very differently under optimisation:

| Category | Example | What you get |
|---|---|---|
| **Implementation-defined** | `(int16_t)40000`, `-8 >> 1` | Documented by the compiler. GCC: modulo 2ᴺ, arithmetic shift. Safe *for that compiler*. |
| **Unspecified** | Order of evaluating `f() + g()` | One of several allowed behaviours, not documented |
| **Undefined (UB)** | `INT_MAX + 1`, `1 << 31`, `(uint8_t)x << 24` when bit 7 set, `x << 32` | **Anything**. The optimiser assumes it never happens. |

The dangerous one is UB, because the optimiser actively *uses* it. This function looks harmless:

```c
bool square_is_large(uint16_t a)
{
    uint32_t r = a * a;          /* a is promoted to int: int * int */
    return r > 0x7FFFFFFFU;      /* true for a = 65535 (4 294 836 225) */
}
```

GCC 10.3 at `-O2` compiles it to:

```armasm title="square_is_large at -O2 — the whole function"
movs  r0, #0    ; return false
bx    lr
```

The reasoning: `a * a` is a signed `int` multiplication. Signed overflow is UB, so the compiler may assume the product is ≤ `INT_MAX` = 0x7FFFFFFF, so `r > 0x7FFFFFFF` is always false. **There is no warning, even with `-Wall -Wextra -Wconversion`.** At `-O0` it computes the "expected" answer, so the bug only exists in the release build. The fix is one cast: `(uint32_t)a * a`.

The same happens with the complement bug: `~a8 == 0xF0` compiles to `movs r0, #0`, a constant `false`. That one at least gets a `-Wsign-compare` warning (*"comparison of promoted bitwise complement of an unsigned value with constant"*).

### Catching UB on the target: the trap sanitizer

GCC's UndefinedBehaviorSanitizer normally needs a runtime library, which bare-metal targets don't have. With **trap mode** it needs nothing: every check becomes an inline test plus a `UDF` (permanently undefined) instruction.

```bash
-fsanitize=undefined -fsanitize-undefined-trap-on-error
```

For `uint32_t shl(uint8_t b) { return b << 24; }` it generates:

```armasm title="UBSan trap mode, verified on arm-none-eabi-gcc 10.3"
lsrs  r3, r0, #7    ; does b have bits above bit 6?
bne.n trap          ; then b << 24 overflows int -> UB
lsls  r0, r0, #24
bx    lr
trap: udf #255      ; UsageFault (UNDEFINSTR) -> HardFault if not enabled
```

It costs Flash and cycles, so use it in **test builds**, not production. Exercise 🔴 turns this into a UsageFault report over UART.

### Memory layout, endianness and alignment

- Cortex-M is **little-endian**: the `uint32_t` 0x80010203 is stored at increasing addresses as `03 02 01 80`. Sensor and network protocols are usually **big-endian**. That's why we rebuild values with shifts, which are endian-independent, and never with `*(uint32_t *)&buf[1]`.
- Cortex-M3/M4/M7 can do **unaligned** `LDR`/`LDRH`/`STR`/`STRH` to normal memory (slower; trappable via `SCB->CCR.UNALIGN_TRP`). `LDRD`, `LDM`/`STM` and every access on **Cortex-M0/M0+** fault on misalignment. Pointer-casting a byte buffer is a portability *and* a crash risk. Pointer casts also break the strict-aliasing rule, which the optimiser relies on.
- Use `memcpy` for type punning if you must: GCC compiles a 4-byte `memcpy` into a single `LDR` when that's allowed.

### Short enums: an ABI trap

`arm-none-eabi-gcc` uses **short enums** (`sizeof(enum { A, B })` is 1). That's fine inside one program, but:

- If one object file is built with `-fno-short-enums` (some vendor libraries are), the linker warns *"uses variable-size enums yet the output is to use 32-bit enums"*, and structs containing enums no longer have the same layout on both sides.
- **Never** put an `enum` in a hardware register map, a protocol frame, or a struct that's stored in Flash or sent over a bus. Use a fixed-width type and cast.

### Access width to peripheral registers

Every register in RM0390 has a defined **access width**, stated at the start of each peripheral's register section. For example GPIO registers accept byte, half-word and word access. CMSIS declares all registers `volatile uint32_t`, so normal code always does 32-bit `LDR`/`STR`. It matters when you deliberately use a narrower pointer. On the newer SPI IP of F0/F3/F7/G4/L4, the **width of the write to `SPIx->DR`** decides whether 1 or 2 frames are sent (*data packing*). A `uint8_t *` cast is required there, and it's a real bug source (A9.2).
````

### The APSR flags that decide signed vs unsigned

After `CMP a, b` the CPU sets four flags in the APSR (*Application Program Status Register*, part of `xPSR`, see A1.2):

| Flag | Set when | Used by |
|---|---|---|
| **N** (negative) | Result bit 31 = 1 | Signed conditions |
| **Z** (zero) | Result = 0 | `EQ`/`NE`, `HI`/`LS` |
| **C** (carry) | No borrow in `a − b` (i.e. a ≥ b unsigned) | Unsigned: `HS`/`LO`/`HI`/`LS` |
| **V** (overflow) | Signed overflow in `a − b` | Signed: `GE`/`LT`/`GT`/`LE` (N ≠ V means "less than") |

The same `CMP` serves both signednesses. The C types choose the condition, and that's where a promotion bug becomes a wrong branch.

### How an expression is evaluated, stage by stage

```mermaid caption="From memory to result: where promotion and truncation happen"
flowchart LR
    M1["uint8_t in SRAM"] -->|"LDRB, zero-extend"| R1["32-bit register"]
    M2["int16_t in SRAM"] -->|"LDRSH, sign-extend"| R2["32-bit register"]
    R1 --> P["Promotion to int<br/>(already done by the load)"]
    R2 --> P
    P --> U["Usual arithmetic conversions<br/>(may reinterpret as unsigned)"]
```

### Line-by-line: the non-obvious lines

| Line | Explanation |
|---|---|
| `static volatile uint8_t s_u8Pattern = 0x0FU;` | `volatile` stops GCC from folding the whole test into a constant at compile time. We *want* the CPU to execute the expression so you can single-step it. (Full story of `volatile` in A0.3.) |
| `#define TYPE_NAME(x) _Generic((x), …)` | C11 `_Generic` selects a string based on the **static type** of `x`. The expression is never evaluated. It's how we prove, on the target, that `a + a` is an `int` and `int32_t` is a `long`. |
| `#pragma GCC diagnostic ignored "-Wsign-compare"` | The buggy line is intentionally buggy. We silence the warning for that line only, and keep it active for the rest of the project. |
| `uint8_t inverted = (uint8_t)~value;` | The fix: truncate the promoted 32-bit result back to 8 bits *before* comparing. |
| `(uint16_t)(now - start)` | Subtraction happens in `int`, and the cast reduces it modulo 2¹⁶. That's exactly the hardware counter's arithmetic. |
| `(int16_t)(uint16_t)(…)` | Two casts: first make the 16-bit pattern explicit, then reinterpret bit 15 as the sign. The conversion to `int16_t` is implementation-defined, and GCC documents it as modulo 2¹⁶. Exercise 🟡 shows a version with no implementation-defined behaviour at all. |
| `"%" PRIu32` | Expands to `"%lu"` on ARM because `uint32_t` is `unsigned long`. The same source is correct on a PC, where it expands to `"%u"`. |
| `static volatile uint32_t s_sumLength` | With a constant length, GCC proves the `uint8_t` index can't wrap and produces identical code. The runtime length measures the realistic case. |
| `(void)RCC->AHB1ENR;` | Reading back after enabling a peripheral clock guarantees the enable has taken effect before the peripheral is touched (A4.5). |
| `USART2->BRR = (CPU_CLOCK_HZ + UART_BAUD/2) / UART_BAUD;` | With 16× oversampling, BRR = f<sub>PCLK</sub> / baud, rounded: (16 000 000 + 57 600) / 115 200 = **139 = 0x8B** (mantissa 8, fraction 11). Real baud rate 115 108 Bd, error **−0.08 %** (A8.2). |
| `USART2->DR = (uint32_t)(uint8_t)*text++;` | `char` → `uint8_t` → `uint32_t`: nothing can be sign-extended into bits 8–31, whatever the signedness of `char`. |
| `(DWT->CYCCNT - start) < ticks` | 32-bit unsigned subtraction wraps correctly when `CYCCNT` overflows (every 2³² / 16 MHz ≈ 268 s). It's the same idea as test T3. |
| `GPIOA->ODR ^= (1UL << LED_PIN);` | A read-modify-write, safe here because no interrupt touches GPIOA. A5.3 explains when you must use `BSRR` instead. |
| `SCB->CPACR \|= (3UL << 20) \| (3UL << 22)` | Grants full access to coprocessors CP10/CP11 (the FPU). The project is built with `-mfloat-abi=hard`, so this must happen before any floating-point instruction runs (A1.6). |

## Common mistakes & debugging

### 1. `~` on a small unsigned type
- **Symptom:** `if (~status == 0xF0)` is never true. A mask built with `~` has 24 extra 1-bits.
- **Why:** `status` is promoted to `int` before `~`, which flips all 32 bits.
- **Diagnose:** `-Wextra` gives *"comparison of promoted bitwise complement of an unsigned value with constant"*. In the disassembly the branch is gone (the result is a constant).
- **Fix:** truncate into a variable first: `uint8_t inv = (uint8_t)~status; if (inv == 0xF0U)`. The one-line form `(uint8_t)~status == 0xF0U` is correct C, but GCC (10.3 and 12, verified) still emits the same warning for it, a known false positive, so a warning-clean codebase uses the two-line form. Or keep masks in `uint32_t` from the start.

### 2. Signed vs unsigned comparison
- **Symptom:** `if (offset < sizeof buffer)` is false for `offset = -1`, so a guard lets a negative index through. Or `for (int32_t i = len - 1; i >= 0U; i--)` never ends.
- **Why:** equal rank, one operand unsigned → the signed one becomes unsigned; −1 → 4 294 967 295.
- **Diagnose:** `-Wsign-compare` (enabled by `-Wextra`) is designed for exactly this. Treat it as an error.
- **Fix:** check the sign first: `(offset >= 0) && ((uint32_t)offset < sizeof buffer)`. Or use one signedness for a variable's whole life.

### 3. A `uint8_t` loop counter with a large bound
- **Symptom:** the device hangs (or the watchdog keeps resetting it) as soon as a buffer grows to 256 entries.
- **Why:** `for (uint8_t i = 0; i < 300; i++)`: `i` wraps 255 → 0 and is always `< 300`. GCC 10.3 compiles the loop to an unconditional branch.
- **Diagnose:** `-Wtype-limits` (in `-Wextra`) warns *"comparison is always true due to limited range of data type"*, but **only when the bound is a constant**. With a runtime bound you get nothing: halt in the debugger and you'll find the PC looping in the same few instructions.
- **Fix:** loop counters are `uint32_t` or `size_t`. Always.

### 4. Elapsed time on a 16-bit counter
- **Symptom:** a timeout on `TIMx->CNT` (16-bit timer) sometimes never fires; an input-capture period is occasionally negative or huge.
- **Why:** `now - start` is computed in `int`, which doesn't wrap at 65 536.
- **Diagnose:** log `now`, `start` and the delta; the failures happen only when `now < start`.
- **Fix:** `(uint16_t)(now - start)`. Used again in A7.4 (input capture) and A7.6 (encoder).

### 5. Losing the sign of sensor data
- **Symptom:** temperatures below 0 °C read as +655 °C; accelerometer axes jump from −1 g to +65 000.
- **Why:** `(msb << 8) | lsb` is an `int` with bit 15 set but bit 31 clear, so it's positive.
- **Diagnose:** the value is exactly 65 536 too large. That's always the signature of a missed 16-bit sign extension.
- **Fix:** `(int16_t)(uint16_t)((msb << 8) | lsb)`, or the portable helper from exercise 🟡.

### 6. Storing a masked flag in a narrow variable
- **Symptom:** the user button on PC13 "never" changes state.

  ```c
  uint8_t level = GPIOC->IDR & GPIO_IDR_ID13;   /* 0x2000 -> truncated to 0x00 */
  ```
- **Why:** assignment to `uint8_t` keeps bits 0–7. Bit 13 is thrown away.
- **Diagnose:** `-Wconversion` warns *"conversion from 'long unsigned int' to 'uint8_t' {aka 'unsigned char'} may change value"*.
- **Fix:** `bool level = (GPIOC->IDR & GPIO_IDR_ID13) != 0U;`. The explicit `!= 0U` makes the intent obvious, and `bool` would convert correctly anyway.

### 7. Shifting a byte into the sign bit
- **Symptom:** `uint32_t v = buf[0] << 24;` "works". With the UB sanitizer the board faults. On a 64-bit host, `uint64_t v = buf[0] << 24` yields `0xFFFFFFFF80000000`.
- **Why:** `buf[0]` is promoted to **signed** `int`; `0x80 << 24` doesn't fit in `int`, which is **undefined behaviour**.
- **Diagnose:** `-fsanitize=undefined -fsanitize-undefined-trap-on-error` → UsageFault at the shift.
- **Fix:** widen first: `(uint32_t)buf[0] << 24`. Write all masks as `1UL << n`.

### 8. `uint16_t × uint16_t` overflow that only fails in Release
- **Symptom:** a power or energy calculation is correct in Debug and silently wrong in Release. There are no warnings.
- **Why:** both operands promote to `int`; 65 535² overflows `int` (UB), so the optimiser assumes it can't happen (see the 🔴 layer, where the function becomes `return false`).
- **Diagnose:** compare `-O0` and `-O2` results; the UBSan trap build faults at the multiplication.
- **Fix:** `(uint32_t)a * b`. Cast **one operand before** the operation, not the result after it.

### 9. `printf` format mismatch
- **Symptom:** warnings *"format '%d' expects argument of type 'int', but argument 2 has type 'int32_t' {aka 'long int'}"*; wrong values when code moves to a 64-bit host test.
- **Fix:** `PRId32` / `PRIu32` / `PRIX32` from `<inttypes.h>`, or cast explicitly: `(long)x` with `%ld`.

### 10. Unit tests pass on the PC, firmware fails on the MCU
- **Symptom:** `char` comparisons such as `if (c < 0)` or `(char)0xFF == -1` behave differently on target and host.
- **Why:** plain `char` is unsigned on ARM and signed on x86.
- **Fix:** compile host tests with **`-funsigned-char`**; never use plain `char` for numbers.

## Best practices & production tips

```callout production title="What professional firmware teams actually do"
- **Warnings are errors.** Build with `-Wall -Wextra -Wconversion -Wsign-conversion -Wshadow -Wformat=2 -Wdouble-promotion` and `-Werror` in CI. `-Wconversion` is noisy on legacy code, so turn it on file by file, but turn it on.
- **Follow a type model.** MISRA C:2012's *essential type model* (rules 10.1–10.8) exists to forbid exactly the implicit conversions in this lesson. Most automotive and medical codebases enforce it with a static analyser (PC-lint Plus, Polyspace, Parasoft, or cppcheck's MISRA add-on).
- **Parse bytes with shifts, never with pointer casts.** One set of helpers (`be16_to_s16`, `be32_to_u32`, `le16_to_u16`…), unit-tested, used everywhere.
- **One time-comparison helper.** `time_elapsed(now, start, timeout)` in the counter's own unsigned width. Nobody writes `now - start` by hand.
- **`_Static_assert` every binary layout**: `_Static_assert(sizeof(frame_t) == 12U, "frame_t must match the wire format");`
- **Suffix every constant that meets a register**: `U` for values, `UL` for masks, as CMSIS does.
- **Test on the host *and* the target.** Host tests catch logic bugs fast; target tests catch ABI differences (`char`, `int32_t`, enum size). Build host tests with `-funsigned-char -fshort-enums` to get closer to the target.
- **Run a UBSan-trap build in the test rack.** Fault handler + UART log (A15.3) turns silent UB into a precise PC address.
- **Use saturation instead of wrap for physical values.** Cortex-M4 has `SSAT`/`USAT` (CMSIS `__SSAT(x, 16)`), so clamping a sensor or PWM value costs one instruction.
- **Prefer 32-bit locals.** They're free on Cortex-M; small types only make sense in arrays, structs that must be packed, and wire formats.
```

### 🟡 Exercise 2: a portable byte-decoding module

Write `bytes.h` with four `static inline` functions and **no implementation-defined behaviour** (so no cast of an out-of-range value to a signed type):

- `bool time_elapsed_u16(uint16_t now, uint16_t start, uint16_t timeout)`
- `int16_t be16_to_s16(const uint8_t *p)`: big-endian two's complement 16-bit
- `uint32_t be32_to_u32(const uint8_t *p)`
- `int32_t be24_to_s32(const uint8_t *p)`: 24-bit two's complement, as produced by many 24-bit ADCs

It must compile with zero warnings under `-Wall -Wextra -Wconversion -Wsign-conversion` and pass these checks: `{FF FF FF}` → −1, `{80 00 00}` → −8 388 608, `{7F FF FF}` → 8 388 607, `{FF 38}` → −200, `{80 00}` → −32 768, `{80 01 02 03}` → 0x80010203, and `time_elapsed_u16(5, 65530, 10)` = true.

**Hints:** the sign bit of an N-bit two's complement number has weight −2ᴺ⁻¹, and all other bits have their normal positive weights. Widen every byte to `uint32_t` *before* shifting it.

````solution title="Show a reference solution (tested on PC and compiled for Cortex-M4)"
```c
/**
 * @file  bytes.h
 * @brief Portable, UB-free helpers for sensor bytes and wrapping tick counters.
 */
#ifndef BYTES_H
#define BYTES_H

#include <stdbool.h>
#include <stdint.h>

/** @brief true when at least @p timeout ticks passed since @p start (16-bit counter). */
static inline bool time_elapsed_u16(uint16_t now, uint16_t start, uint16_t timeout)
{
    return (uint16_t)(now - start) >= timeout;   /* modulo-2^16 difference */
}

/** @brief Big-endian 16-bit two's complement -> int16_t, no implementation-defined cast. */
static inline int16_t be16_to_s16(const uint8_t *p)
{
    const uint16_t u = (uint16_t)(((uint16_t)p[0] << 8) | p[1]);
    return (int16_t)((int32_t)(u & 0x7FFFU) - (int32_t)(u & 0x8000U));
}

/** @brief Big-endian 32-bit unsigned. Each byte is widened BEFORE shifting. */
static inline uint32_t be32_to_u32(const uint8_t *p)
{
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8)  |  (uint32_t)p[3];
}

/** @brief Big-endian 24-bit two's complement (e.g. 24-bit ADC) -> int32_t. */
static inline int32_t be24_to_s32(const uint8_t *p)
{
    const uint32_t u = ((uint32_t)p[0] << 16) | ((uint32_t)p[1] << 8) | (uint32_t)p[2];
    /* bit 23 has weight -2^23: subtract it instead of relying on a cast */
    return (int32_t)(u & 0x7FFFFFUL) - (int32_t)(u & 0x800000UL);
}

#endif /* BYTES_H */
```

**Why it's portable:** in `be24_to_s32` both operands of the subtraction are in the range 0 … 8 388 608, so they fit in `int32_t`, and the subtraction produces the negative value directly. There's no conversion of an out-of-range value, so the result is the same on every conforming compiler. The same trick works in `be16_to_s16`: the result is in −32 768 … 32 767, so the final `(int16_t)` cast is always in range.
````

## Cheat sheet

```callout tip title="A0.1 on one screen"
**Sizes (arm-none-eabi-gcc):** `char` 1 (unsigned!) · `short` 2 · `int` 4 · `long` 4 · `long long` 8 · pointer 4 · `size_t` = `unsigned int` · `int32_t` = `long` · `enum` = smallest that fits · `bool` 1.

**Rule 1: promotion.** Anything narrower than `int` becomes `int` before arithmetic, bitwise ops, shifts and comparisons. That includes `uint8_t` and `uint16_t`.

**Rule 2: conversions.** Mixed types after promotion: same signedness → wider type wins; signed vs unsigned of **equal or lower rank** → **signed becomes unsigned** (−1 → 4 294 967 295).

**Rule 3: assignment truncates.** Storing into N bits keeps the value mod 2ᴺ (defined for unsigned targets, implementation-defined for signed; GCC does mod 2ᴺ).

**Seven bugs → seven fixes**
| Bug | Fix |
|---|---|
| `~u8 == 0xF0` | `uint8_t inv = (uint8_t)~u8; inv == 0xF0U` |
| `s32 < u32` with negatives | `(s < 0) \|\| ((uint32_t)s < u)` |
| `now - start` (16-bit) | `(uint16_t)(now - start)` |
| `(msb << 8) \| lsb` signed | `(int16_t)(uint16_t)(…)` |
| `b << 24`, `1 << 31` | `(uint32_t)b << 24`, `1UL << 31` |
| `u16 * u16` | `(uint32_t)a * b` |
| `uint8_t f = reg & (1UL << 13)` | `bool f = (reg & (1UL << 13)) != 0U` |

**Printing:** `PRId8/16/32/64`, `PRIu32`, `PRIX32` from `<inttypes.h>`.
**Literals:** decimal → `int/long/long long` only; hex may become unsigned; add `U`/`UL`.
**Flags:** `-Wall -Wextra -Wconversion -Wsign-conversion`; test builds: `-fsanitize=undefined -fsanitize-undefined-trap-on-error`.
**Asm tells:** `UXTB/UXTH` = truncation cost; `SXTB/SXTH` = sign extension; `CS/CC/HI/LS` after `CMP` = unsigned compare.
```
