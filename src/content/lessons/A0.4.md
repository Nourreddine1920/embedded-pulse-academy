## Learning objectives

By the end of this lesson you will be able to:

1. **Explain** memory-mapped I/O: why a Cortex-M4 has no I/O instructions, and how an ordinary `LDR`/`STR` to `0x4002 0014` changes a pin.
2. **Locate** any STM32F446 register from RM0390 as *region → bus → peripheral base → offset*, and compute its absolute address by hand (for example `GPIOA->ODR` = `0x4002 0014`).
3. **Write** a raw register access `*(volatile uint32_t *)0x40020014UL`, justify every token in it, and wrap it in a `REG32()` macro.
4. **Apply** pointer arithmetic correctly on register pointers: `p + 5` on a `uint32_t *` moves 20 bytes, not 5, and the access width follows the pointer type.
5. **Read** the CMSIS qualifiers `__I`, `__O`, `__IO` (and `__IM`, `__OM`, `__IOM`), state which one the compiler actually enforces, and use `const volatile` pointers to make read-only views.
6. **Design** a driver that receives its register base as a parameter, so the same code runs on the STM32 and in a unit test against a fake register array.

## Why this matters

A team ports a motor controller from an STM32F4 to a newer part. The HAL is gone, so a contractor writes the GPIO layer by hand. In the first bring-up the brake output never engages. Nothing faults, nothing warns, and the code "obviously" writes the right register:

```c
#define GPIOB_BASE   0x40020400UL
uint32_t *gpiob = (uint32_t *)GPIOB_BASE;

gpiob[GPIO_BSRR_OFS] = BRAKE_PIN;        /* GPIO_BSRR_OFS = 0x18 */
```

Two bugs sit in that one line. `gpiob[0x18]` is **24 words** past the base, `0x4002 0460`: a reserved address inside the GPIOB block, so the write goes nowhere. And the pointer isn't `volatile`, so in the release build the compiler was entitled to merge or drop the "useless" stores anyway. A pointer to a register is the most basic construct in firmware, and each of its parts (the integer, the cast, the qualifier, the type width, the offset arithmetic) can be silently wrong.

Every register access in this course, whether you write it or a HAL writes it for you, is one of these pointers. You'll use this lesson directly in:
- Register maps as structs (A0.5) and header hygiene (A0.6)
- The memory map and bus matrix (A1.4), the vector table (A2.2) and fault analysis with `BFAR` (A3.3)
- RCC clock enables (A4.5), GPIO drivers and their unit tests (A5.2, A5.6), NVIC registers (A6.1), and DMA source/destination addresses (A14.1)

## Concept explanation

````layer beginner
### Registers are memory addresses

On a PC, programs talk to hardware through the operating system. On a microcontroller, your code talks to hardware **directly**, and the way it does that is surprisingly simple: every control register of every peripheral has an **address**, just like a variable in RAM.

```callout analogy title="Analogy: a street of letterboxes"
Picture one very long street with 4 billion house numbers. Most houses are storage (Flash and RAM): you put a letter in, and it's still there when you come back. But the houses from number `0x4000 0000` onwards are different. They're **control panels**. Dropping the letter "0x20" into box `0x4002 0018` doesn't store anything: it *switches on a light* (the green LED LD2). Reading box `0x4002 0010` tells you *what the buttons are doing right now*. Same street, same letterboxes, same way of posting a letter, but what happens behind the door is completely different.
```

This is called **memory-mapped I/O**. The Cortex-M4 has no special "input/output" instructions. It uses the same load (`LDR`) and store (`STR`) instructions for a variable in RAM and for a GPIO register. What's at the address decides what happens.

### The STM32F446 memory map

The 4 GB address space is divided into regions. Walk through it from the top down to a single register:

The numbers to remember:

| Address | What lives there |
|---|---|
| `0x0800 0000` | Flash: your program and `const` data (A0.3) |
| `0x1FFF 7A10` | Factory data: 96-bit unique ID; flash size at `0x1FFF 7A22` |
| `0x2000 0000` | SRAM (128 KiB): your variables and the stack |
| `0x4000 0000` | Peripherals: APB1, APB2, AHB1 (GPIO, RCC), AHB2 |
| `0xE000 0000` | The Cortex-M4's own registers: SysTick, NVIC, SCB |

### From a number to a register, in C

C lets you turn any integer into a pointer with a cast, and then read or write through it. Here's the complete line that switches LD2 on, from the reference manual's numbers alone:

```c
*(volatile uint32_t *)0x40020018UL = 0x20UL;   /* GPIOA_BSRR: set PA5 */
```

Read it from the inside out:

| Piece | Meaning |
|---|---|
| `0x40020018UL` | The address from RM0390: GPIOA base `0x4002 0000` + BSRR offset `0x18` |
| `(volatile uint32_t *)` | "Treat that number as the address of a 32-bit value that can change or matter at any time" |
| `*` in front | "…and I mean *the thing at that address*" |
| `= 0x20UL` | Store the value: bit 5 set = pin PA5 high |

Every piece matters. The next animation builds the line token by token and shows the real machine code:

### Why `volatile` again?

You met `volatile` in A0.3. For registers, it's not optional. Without it, the compiler treats the address like ordinary RAM: it may skip a read it thinks it already knows, or drop a write it thinks is overwritten. For a register, each read and each write *is* the point. So: **every pointer to hardware is a pointer to `volatile`**.

### You rarely write raw addresses, but everything is one

In real code you write `GPIOA->BSRR = GPIO_BSRR_BS5;`. It looks nothing like the line above, but after the preprocessor has run, it's the same thing. `GPIOA` is defined in ST's header as `((GPIO_TypeDef *) GPIOA_BASE)`: a cast of the number `0x4002 0000`. Understanding the raw form means you can read any header, debug any driver, and work on a chip that has no HAL at all.
````

````layer intermediate
### Finding a register's address in RM0390

Every register has a two-part address: a **base** for the peripheral and an **offset** for the register inside it.

1. *Memory map* table (RM0390, "Memory map" → "Register boundary addresses"): find the peripheral. GPIOA: `0x4002 0000 – 0x4002 03FF`, bus **AHB1**. RCC: `0x4002 3800`. USART2: `0x4000 4400`, bus **APB1**.
2. The peripheral's *register map* (at the end of its chapter): find the offset. GPIO `ODR`: `0x14`. RCC `AHB1ENR`: `0x30`.
3. Add them: `0x4002 0000 + 0x14 = 0x4002 0014`.

The CMSIS device header `stm32f446xx.h` builds the same numbers in layers, which is worth recognising:

```c
#define PERIPH_BASE           0x40000000UL
#define AHB1PERIPH_BASE       (PERIPH_BASE + 0x00020000UL)
#define GPIOA_BASE            (AHB1PERIPH_BASE + 0x0000UL)
#define RCC_BASE              (AHB1PERIPH_BASE + 0x3800UL)
#define GPIOA                 ((GPIO_TypeDef *) GPIOA_BASE)
#define UID_BASE              0x1FFF7A10UL
#define FLASHSIZE_BASE        0x1FFF7A22UL
```

The `UL` suffix keeps every address an `unsigned long` (32 bits on ARM), so the arithmetic can't overflow a signed `int` (A0.1).

### Three ways to write the same access

| Style | Code | Where you see it |
|---|---|---|
| Raw cast | `*(volatile uint32_t *)0x40020014UL` | Bring-up code, bootloaders, one-off debug |
| Macro | `REG32(LAB_GPIOA_BASE + GPIO_ODR_OFS)` | Minimal projects without a device header |
| Base + offset | `*reg_at(port, GPIO_ODR_OFS)` | Drivers that take the port as a parameter |
| CMSIS struct | `GPIOA->ODR` | Almost all production code |

They compile to the **same instructions**. The struct form (A0.5) is preferred because the compiler knows every offset and type, but the other three are what the struct is made of. A `REG32` macro is a single cast:

```c
#define REG32(addr)   (*(volatile uint32_t *)(uintptr_t)(addr))
```

`uintptr_t` (from `<stdint.h>`) is "an unsigned integer wide enough to hold a pointer". Going through it states the intent and keeps the conversion well-defined on a 64-bit PC, where the lab's unit tests run.

### Pointer arithmetic counts elements, not bytes

This is the most common bug in hand-written register code. For a pointer `p` of type `T *`, `p + n` points `n × sizeof(T)` **bytes** further:

| Expression | Address | Why |
|---|---|---|
| `(volatile uint32_t *)0x40020000 + 5` | `0x4002 0014` | 5 × 4 bytes: `ODR` |
| `(volatile uint32_t *)0x40020000 + 0x14` | `0x4002 0050` | 0x14 × 4 = 0x50: **not** `ODR` |
| `(volatile uint8_t *)0x40020000 + 5` | `0x4002 0005` | 5 × 1 byte: the second byte of `MODER` |
| `(volatile uint16_t *)0x1FFF7A10 + 9` | `0x1FFF 7A22` | 9 × 2 bytes: the flash-size halfword |

The reference manual gives **byte** offsets. So either index a `uint32_t *` with `offset / 4`, or do the addition on integers before casting. The lab's `reg_at(base, byteOffset)` does the first, so the offsets in the code are the numbers in the manual.

### The pointer type sets the access width

`uint32_t *` produces a 32-bit load (`LDR`), `uint16_t *` a 16-bit one (`LDRH`), `uint8_t *` an 8-bit one (`LDRB`). The bus transfers exactly that size, and some peripherals care. Each register chapter of RM0390 ends with a sentence like *"The peripheral registers can be accessed by words (32 bits)"* or *"by half-words (16 bits) or words"*. The flash-size value at `0x1FFF 7A22` is **16 bits**, so it's read through a `uint16_t *`. Read it as 32 bits and you get the neighbouring two bytes as well.

### The CMSIS qualifiers `__I`, `__O`, `__IO`

`core_cm4.h` defines:

```c
#ifdef __cplusplus
  #define   __I     volatile             /*!< Defines 'read only' permissions */
#else
  #define   __I     volatile const       /*!< Defines 'read only' permissions */
#endif
#define     __O     volatile             /*!< Defines 'write only' permissions */
#define     __IO    volatile             /*!< Defines 'read / write' permissions */

/* following defines should be used for structure members */
#define     __IM     volatile const      /*! Defines 'read only' structure member permissions */
#define     __OM     volatile            /*! Defines 'write only' structure member permissions */
#define     __IOM    volatile            /*! Defines 'read / write' structure member permissions */
```

So only **read-only** is enforced, via `const`. "Write-only" can't be expressed in C, and `__O` is plain `volatile`. And ST's device header declares nearly every peripheral register `__IO`, including read-only ones like `GPIOx->IDR` and `DBGMCU->IDCODE`. The Cortex core headers are stricter: `SCB->CPUID` is `__IM`.

```anim
io-qualifiers
```

The practical rule: the qualifiers are documentation, and the **access column in RM0390** is the truth. When your own code hands out a read-only register, give it the type `const volatile uint32_t *` and the compiler will check it for you.

### `const volatile`: the read-only view

`const` and `volatile` aren't opposites. `const` limits *what your code may do* (no writes). `volatile` describes *the object* (it can change by itself, and every access counts). A status or ID register is exactly both:

```c
const volatile uint32_t *const idcode = (const volatile uint32_t *)0xE0042000UL;
/*    ^^^^^^^^^^^^^^ the register: read-only, re-read every time
                                    ^^^^^ the pointer itself never changes */
```

### Design for testability: pass the base in

A driver that writes `GPIOA->ODR` directly can only run on the chip. A driver that receives `volatile uint32_t *port` and computes `port + offset` runs **anywhere**: on the STM32 you pass `(volatile uint32_t *)0x40020000`, and in a unit test on your PC you pass an ordinary `uint32_t fake[10]`. The fake has the same layout as the ten GPIO registers, so the driver can't tell the difference, and the test inspects `fake[6]` to see exactly what was written to `BSRR`. The lab is built around this.

### Reading the documentation

- **RM0390**: *Memory map* and the *register boundary addresses* table (base and bus of each peripheral); each chapter's *register map* (offsets and reset values); *Device electronic signature* (unique ID, flash size); *Debug support → MCU device ID code* (`DBGMCU_IDCODE`).
- **Cortex-M4 Devices Generic User Guide (DUI 0553)**: *Memory model* (regions and memory types) and *System control block* (`CPUID` at `0xE000 ED00`).
- **Your headers**: `core_cm4.h` (qualifiers, `SCB_Type`), `stm32f446xx.h` (bases, `GPIO_TypeDef`, `UID_BASE`).
````

````layer advanced
### What register accesses compile to (GCC 10.3, `-O2`, verified)

All from `arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 -O2`, disassembled with `objdump -d`:

| C | Cortex-M4 instructions |
|---|---|
| `REG32(0x40020018UL) = 0x20UL;` | `ldr r3, [pc, #4]` (literal `0x40020000`) · `movs r2, #32` · `str r2, [r3, #24]` |
| `GPIOA->MODER = 1; GPIOA->ODR = 2; GPIOA->BSRR = 0x20;` | **one** `ldr r3, =0x40020000`, then `str r0, [r3, #0]` · `str r1, [r3, #20]` · `str r2, [r3, #24]` |
| Two stores to `*(uint32_t *)0x40020018` (**no** `volatile`) | `mov.w r2, #0x200000` · `str r2, [r3, #24]`: the first store is **deleted** |
| The same two stores through `REG32()` | `str r1, [r3, #24]` · `str r2, [r3, #24]`: both kept, in order |
| `while ((*(uint32_t *)0x40004400 & 0x80) == 0) {}` (no `volatile`) | `ldr.w r3, [r3, #1024]` once, then `b.n .` : an **infinite loop on itself** |
| The same loop through `REG32()` | `ldr.w r3, [r2, #1024]` · `lsls r3, r3, #24` · `bpl.n` back to the `ldr` |
| `*(const volatile uint16_t *)0x1FFF7A22` | `ldr r3, =0x1FFF7A00` · `ldrh r0, [r3, #34]` |
| `*(const volatile uint32_t *)0x1FFF7A22` | `ldr r3, =0x1FFF7000` · `ldr.w r0, [r3, #2594]`: an **unaligned** word load |
| `*(volatile uint8_t *)0x40020014` | `ldrb r0, [r3, #20]` |
| `return p[5];` (`volatile uint32_t *p`) | `ldr r0, [r0, #20]`: the scaling by 4 is done at compile time |

Four things to notice:

1. **A 32-bit address doesn't fit in an instruction.** GCC puts the peripheral base in a *literal pool* after the function and loads it PC-relative. Then every register of that peripheral is reached with an **immediate offset** (`[r3, #24]`). That's why the struct form is cheap: one base load, then one instruction per register.
2. **Base selection is clever.** For `0x4000 4400` GCC chose `mov.w r3, #0x40004000` (a *modified immediate*, A0.2) plus offset `#1024`, avoiding the literal pool entirely. For `0x1FFF 7A22` it picked base `0x1FFF 7A00` for the `LDRH` (whose immediate offset range is smaller) and `0x1FFF 7000` for the `LDR.W` (12-bit offset, 0–4095).
3. **Without `volatile` the polling loop becomes `b.n .`**: one read, then spin forever. It's exactly A0.3's hoisting bug, now on a status register. The UART never "becomes ready" in a release build.
4. **The unaligned load is legal on the M4** in Normal memory (the code region is Normal) unless `SCB->CCR.UNALIGN_TRP` is set, so it doesn't fault. It silently returns the flash size in the low half and the next two bytes in the high half. In the Device-type peripheral region, unaligned accesses are UNPREDICTABLE in the ARMv7-M architecture. Never rely on them.

### What the C standard actually promises

- **Integer → pointer** (ISO C11 §6.3.2.3 ¶5): *implementation-defined*, and the result "might not be correctly aligned, might not point to an entity of the referenced type". GCC documents its choice (*C Implementation → Arrays and pointers*): when the sizes match, "the bits are unchanged". On ARM, `int`, `long` and pointers are all 32 bits, so `0x40020018UL` becomes exactly that address.
- **`uintptr_t`** (§7.20.1.4) is optional in the standard, but present on every toolchain you'll use. It's the right type for addresses held as integers, and for printing them (`PRIXPTR`).
- **Accessing a `volatile` object** (§5.1.2.3, §6.7.3 ¶7): each access is a *side effect* and must be evaluated strictly by the rules of the abstract machine. What counts as "an access" is implementation-defined. GCC performs one access of the declared width per read or write in the source, which is what the table above shows.
- **Initialising a pointer from an integer without a cast** is a constraint violation. GCC 10.3 reports it only as a warning (verified): *"initialization of 'volatile uint32_t \*' … from 'long unsigned int' makes pointer from integer without a cast [-Wint-conversion]"*. Treat it as an error (`-Werror=int-conversion`).
- **Writing through `const`**: a hard error. Real GCC output for `SCB->CPUID = 0U;` with an `__IM` member: *"error: assignment of read-only member 'CPUID'"*.

### Memory types: why a store may not have happened "yet"

The Cortex-M4 default memory map gives each region a **memory type** (DUI 0553, *Memory model*): the code and SRAM regions are *Normal*, `0x4000 0000–0x5FFF FFFF` is *Device*, and the private peripheral bus `0xE000 0000–0xE00F FFFF` is *Strongly-ordered*. Device accesses keep their order relative to each other and aren't merged by the hardware, but the processor's write buffer can let the CPU carry on **before** a store to a peripheral completes on a slower APB bus. Two consequences you'll meet later:

- **Enabling a peripheral clock and using it immediately.** STM32 errata sheets (for the F446, ES0298, *"Delay after an RCC peripheral clock enabling"*) require a short delay. The standard fix is a read-back, `(void)RCC->AHB1ENR;`, which is exactly what the `__HAL_RCC_GPIOA_CLK_ENABLE()` macro does. The lab's `main_reg.c` does it too.
- **Clearing an interrupt flag at the end of an ISR.** If the write hasn't reached the peripheral when the handler returns, the interrupt can fire a second time. The fix is a `__DSB()` or a read-back (A6.x).

### Why CMSIS uses a macro and not a pointer variable

`#define GPIOA ((GPIO_TypeDef *) GPIOA_BASE)` is a constant expression, so it costs no RAM, and the compiler can fold `&GPIOA->BSRR` to `0x4002 0018` at compile time. A global `GPIO_TypeDef *const gpioa = …;` would be equivalent at `-O2` within one file, but a *non-const* pointer variable forces a load of the pointer before every access. A third technique, common in C++ and some RTOS BSPs, is to declare `extern GPIO_TypeDef GPIOA_regs;` and place the symbol at `0x4002 0000` in the linker script. It gives the debugger a real symbol, at the price of a linker-script dependency.

### GCC ≥ 11 and small constant addresses

Newer GCCs assume that addresses below 4 KiB can't hold objects, and warn when you dereference one. Verified with GCC 12.1 on the host, for `*(volatile uint32_t *)0x00000020UL = 1U;`: *"warning: array subscript 0 is outside array bounds of 'volatile uint32_t[0]' [-Warray-bounds]"*. ARM GCC 10.3 is silent. This hits code that reads the vector table at address 0 or a peripheral on a chip whose map starts low. The fix is `--param=min-pagesize=0` (verified to silence it on GCC 12.1), or taking the address from a linker symbol.

### Probing addresses that might not exist

A load from an unmapped address produces a **precise BusFault** (`CFSR.PRECISERR`, faulting address in `BFAR`), which escalates to HardFault if the BusFault handler isn't enabled. Boot code that needs to detect optional hardware can suppress this with `SCB->CCR.BFHFNMIGN` while running at priority −1 (`FAULTMASK` set). It's exercise 🔴 3, and fault analysis is lesson A3.3.
````

### Line-by-line: the non-obvious lines

| Line | Explanation |
|---|---|
| `#define REG32(addr) (*(volatile uint32_t *)(uintptr_t)(addr))` | Integer → `uintptr_t` → pointer to volatile word → dereferenced lvalue. The outer parentheses let you write `REG32(a) \|= m` and `&REG32(a)` safely. |
| `return base + (byteOffset / (uint32_t)sizeof(uint32_t));` (`reg_at`) | `base` counts in words, and the RM counts in bytes. Dividing once, here, lets every caller use the manual's offsets unchanged. |
| `_Static_assert(LAB_GPIOA_BASE + GPIO_ODR_OFS == 0x40020014UL, …)` | The compiler checks the address arithmetic at build time. A typo in a base breaks the build, not the board. |
| `_Static_assert(GPIOA_BASE == LAB_GPIOA_BASE, …)` (`main_reg.c`) | The hand-written map and ST's header must agree. If you ever port to another part, this is the first thing that fails. |
| `_Static_assert(offsetof(GPIO_TypeDef, BSRR) == GPIO_BSRR_OFS, …)` (`main.c`) | The CMSIS struct layout matches the RM offsets: the struct *is* a base-plus-offset table (A0.5). |
| `volatile uint32_t *port;` (in `LedDrv`) | The driver stores a pointer, not an address constant. That single design choice makes it testable. |
| `*reg_at(led->port, GPIO_BSRR_OFS) = 1UL << led->pin;` | A single write to `BSRR`: atomic, no read (A0.2). |
| `const volatile uint32_t *idcode;` (`DevInfo_Sources`) | Read-only by type. `*src->idcode = 0;` would not compile, even though ST declares `IDCODE` as `__IO`. |
| `out->uid[1] = src->uid[1];` | Element 1 of a `uint32_t` array is 4 bytes on: `0x1FFF 7A14`. |
| `const volatile uint16_t *flashKiB;` | The flash size is a 16-bit item. The pointer type makes the compiler emit `LDRH`. |
| `LedDrv_Init(&led, (volatile uint32_t *)LAB_GPIOA_BASE, LED_PIN);` | **The only cast** from an integer to a pointer in the application. Everything below it is typed pointers. |
| `fake[W_MODER] = MODER_RESET_GPIOA \| 0x000000A0UL;` (self-test) | Starts the fake from the real board state (reset value plus the UART pins), so the test checks that the SWD bits survive. |
| `fake[W_ODR] = 0x00000020UL;` (self-test) | A fake has no hardware behind it: writing `BSRR` doesn't update `ODR`. The test plays the peripheral's part itself. That's the main limit of register fakes. |
| `REG32(LAB_RCC_BASE + RCC_AHB1ENR_OFS) \|= (1UL << RCC_AHB1ENR_GPIOAEN_BIT);` | Exactly what `RCC->AHB1ENR \|= RCC_AHB1ENR_GPIOAEN` expands to. The `(void)` read-back that follows waits for the clock to be active (errata; A4.5). |
| `(uintptr_t)&REG32(…)` | Taking the address of the dereferenced cast gives back the pointer, to compare it with `&GPIOA->MODER`. |

## Common mistakes & debugging

### 1. Byte offset used as an index
- **Symptom:** writes "to BSRR" do nothing; reads return 0. No fault.
- **Why:** `gpio[0x18]` on a `uint32_t *` is 0x18 **words** = 0x60 bytes further: `0x4002 0060`, a reserved address inside the GPIOA block.
- **Diagnose:** print `(uintptr_t)&gpio[0x18]`, or look at the store's address in the disassembly.
- **Fix:** index with `offset / 4`, use `reg_at(base, offset)`, or better, the CMSIS struct.

### 2. Missing `volatile` in the cast
- **Symptom:** works at `-O0`, hangs or skips outputs at `-O2`. A polling loop spins forever; only the last of several writes happens.
- **Why:** the compiler treats the address as ordinary memory. Verified: the non-volatile polling loop compiles to one `LDR` followed by `b.n .` (a branch to itself).
- **Fix:** every hardware pointer is `volatile T *`. Use `REG32()` or CMSIS types so you can't forget it.

### 3. Wrong access width
- **Symptom:** the flash size reads as a huge number; a byte write to a word-only peripheral register is ignored or changes neighbouring bits.
- **Why:** the pointer type decides `LDRB`/`LDRH`/`LDR`. `*(uint32_t *)0x1FFF7A22` reads the flash size **plus** the next two bytes (verified: `ldr.w r0, [r3, #2594]`, an unaligned word load).
- **Fix:** match the width the RM states: `uint16_t` for `FLASH_SIZE`, `uint32_t` for peripheral registers unless the chapter explicitly allows byte or half-word access.

### 4. Peripheral clock not enabled
- **Symptom:** a register reads `0x00000000` and ignores every write, even though the address is right.
- **Why:** on STM32, a peripheral whose RCC enable bit is off doesn't respond: writes are lost, and reads return 0.
- **Fix:** enable the clock in `RCC_AHB1ENR`/`APB1ENR`/`APB2ENR` first, and read the enable register back before the first access (the errata delay, A4.5).

### 5. Integer-to-pointer conversion without a cast, or through a signed type
- **Symptom:** *"makes pointer from integer without a cast [-Wint-conversion]"*. On a 64-bit PC test build, `int addr = 0xE0042000;` becomes a negative number and is sign-extended to `0xFFFFFFFFE0042000`.
- **Fix:** keep addresses in `uintptr_t` or `...UL` constants, and convert with an explicit cast in exactly one place. Build with `-Werror=int-conversion`.

### 6. Trusting `__IO` / `__O`
- **Symptom:** `GPIOA->IDR = 0;` or `DBGMCU->IDCODE = 0;` compiles without a warning and has no effect. Reading `BSRR` to "verify" a write always gives 0.
- **Why:** ST declares almost everything `__IO`, and `__O` isn't enforceable in C. Only `__I`/`__IM` (`const`) is checked.
- **Fix:** check the access column in the RM. Verify writes through the register that reflects them (`ODR` for `BSRR`). Give read-only views the type `const volatile`.

### 7. Dereferencing a real address in a host test
- **Symptom:** the unit test crashes with a segmentation fault (Windows: access violation).
- **Why:** `0x4002 0000` isn't mapped in your PC process.
- **Fix:** inject the base address (the lab's `LedDrv`, `DevInfo_Sources`). Test logic on the PC against fakes; test addresses with `_Static_assert` and on the target.

### 8. HardFault on a typo'd address
- **Symptom:** the board ends up in `HardFault_Handler` right after a register access.
- **Why:** the address is in a **reserved** range (for example `0x4000 8000`: APB1 ends at `0x4000 7FFF`). The bus returns an error, which becomes a precise BusFault and then a HardFault.
- **Diagnose:** in the debugger, `SCB->CFSR` shows `PRECISERR` + `BFARVALID`, and `SCB->BFAR` holds the bad address (A3.3).
- **Fix:** compare the address with RM0390's register boundary table; add a `_Static_assert` for every hand-written address.

### 9. `-Warray-bounds` on a constant low address (GCC ≥ 11)
- **Symptom:** *"array subscript 0 is outside array bounds of 'volatile uint32_t[0]'"* on `*(volatile uint32_t *)0x00000020UL` (verified on GCC 12.1). ARM GCC 10.3 is silent, so the warning appears when you upgrade the toolchain.
- **Fix:** `--param=min-pagesize=0` (verified on GCC 12.1), or get the address from a linker symbol. Don't just disable `-Warray-bounds` globally.

### 10. Pointer to the register vs pointer in the register
- **Symptom:** `volatile uint32_t *reg = &GPIOA->ODR;` works, but `uint32_t volatile_addr = GPIOA->ODR;` then `*(uint32_t *)volatile_addr` crashes.
- **Why:** the second line reads the register's **contents** and then uses the value as an address.
- **Fix:** name variables `...Reg` or `...Addr` for pointers and addresses, and `...Value` for contents. Register *values* are rarely addresses; DMA address registers (A14.1) are the exception, and those take `(uint32_t)&buffer`.

## Best practices & production tips

```callout production title="How professional code reaches registers"
- **One cast, at the edge.** The integer → pointer conversion happens in exactly one place: the device header, a board file, or one `Init()` call. Everything else passes typed pointers.
- **Prefer the CMSIS struct** (`GPIOA->ODR`) in application code. It fixes the offset, the width and the `volatile` in one definition that ST has already tested. Raw `REG32()` is for bring-up, bootloaders and headers.
- **`_Static_assert` every hand-written address and offset** against the RM (and against the vendor header when both exist): `_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x18, "…");`.
- **Inject register bases into drivers** (`volatile uint32_t *port` or `GPIO_TypeDef *port`). It's how production teams unit-test drivers on the build server without hardware, and how one driver serves GPIOA…GPIOH.
- **Make read-only views `const volatile`**, whatever the vendor header says.
- **Match the RM access width.** A `uint8_t *` to a word-only register is a latent bug.
- **Enable, then read back, the peripheral clock** before the first access.
- **Keep addresses unsigned** (`UL`, `uintptr_t`). Never store an address in `int`.
- **MISRA C:2012** flags integer ↔ pointer casts (Rule 11.4, advisory) and pointer ↔ integer mixing (Rule 11.6). Register access is the textbook justified deviation: isolate it in one module and document it (A0.6).
```

## Cheat sheet

```callout tip title="A0.4 on one screen"
**Memory-mapped I/O:** registers are addresses; `LDR`/`STR` reach them like RAM. Region → bus → peripheral base → offset.

| Address | What |
|---|---|
| `0x0800 0000` | Flash |
| `0x1FFF 7A10` / `7A22` | UID (3 × 32-bit) / flash size (16-bit, KiB) |
| `0x2000 0000` | SRAM 128 KiB |
| `0x4000 0000` / `0x4001 0000` / `0x4002 0000` | APB1 / APB2 / AHB1 |
| `0x4002 0000` | GPIOA (`+0x10` IDR, `+0x14` ODR, `+0x18` BSRR) |
| `0x4002 3800` | RCC (`+0x30` AHB1ENR, `+0x40` APB1ENR) |
| `0xE000 ED00` / `0xE004 2000` | SCB CPUID / DBGMCU IDCODE |

**The idiom:** `*(volatile uint32_t *)0x40020018UL = x;` · macro `#define REG32(a) (*(volatile uint32_t *)(uintptr_t)(a))`

**Pointer arithmetic:** `p + n` moves `n × sizeof(*p)` bytes. RM offsets are bytes: index `uint32_t *` with `offset / 4`.

**Width = pointer type:** `uint32_t *` → `LDR`, `uint16_t *` → `LDRH`, `uint8_t *` → `LDRB`. Match the RM.

**Qualifiers:** `__I`/`__IM` = `volatile const` (enforced) · `__O`/`__OM` = `volatile` (not enforced) · `__IO`/`__IOM` = `volatile`. ST headers use `__IO` almost everywhere; the RM is the truth.

**Read-only view:** `const volatile uint32_t *`. **Testable driver:** take `volatile uint32_t *base` as a parameter.

**Checklist:** `volatile` ✓ · `UL`/`uintptr_t` ✓ · byte offset ÷ 4 ✓ · width ✓ · clock enabled ✓ · `_Static_assert` the address ✓
```
