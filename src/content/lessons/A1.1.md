## Learning objectives

By the end of this lesson you will be able to:

1. **Explain** the split between *Arm* (designs the core) and *ST* (builds the chip around it): which parts of an STM32 are Arm's (CPU, NVIC, SysTick, MPU, FPU, debug blocks) and which are ST's (Flash, SRAM, RCC, GPIO, UART, …).
2. **Compare** Cortex-M0, M0+, M3, M4(F), M7 and M33 on architecture, pipeline, hardware divide, DSP, FPU, bit-banding and security, and **choose** a core for a requirement.
3. **Map** the STM32 series (F0, G0, F1, F4, F7, H7, L4, L5, …) to their cores, and say which family the NUCLEO-F446RE belongs to.
4. **Decode** `SCB->CPUID` into implementer, architecture, part number and revision (`0x410FC241` = Cortex-M4 r0p1), and tell the *core* identity apart from the *device* identity in `DBGMCU->IDCODE`.
5. **Read** the feature registers (`MVFR0`, `ID_ISAR0`, `DWT->CTRL`, `MPU->TYPE`, `CPACR`) to find out whether the FPU, hardware divide, cycle counter and MPU exist and whether the FPU is switched on.
6. **Predict** from the compiler flags (`-mcpu`, `-mfpu`, `-mfloat-abi`) which operations run as one instruction and which become library calls, and recognize the double-precision trap on a single-precision FPU.

## Why this matters

A team prototypes a motor-control loop on a NUCLEO-F446RE. It filters currents with `float` and calls `sqrt()`, `/` and a few 64-bit sums, and the 20 kHz loop has headroom. For the product, purchasing swaps in a cheaper STM32G0, a Cortex-M0+. The code compiles with no error and no warning. On the first run the control loop misses its deadline, and nobody can see why: the source is unchanged.

Nothing was *wrong*. The M0+ has no divide instruction, no 64-bit multiply, no FPU, and `sqrt()` of a float was never a single instruction, even on the F4. Each of those became a call into a software library, with a different cost. The same C source means different machine code on every core, and "Cortex-M" is a family of at least six different processors.

You use this lesson's vocabulary in every later lesson. You'll use it directly in:
- The core registers, modes and the stack pointers (A1.2, A1.3), the memory map and bus matrix (A1.4), the FPU and `-mfloat-abi` (A1.6)
- The DWT cycle counter and SWV/ITM, which exist only on some cores (A3.5)
- NVIC priority bits, which each vendor chooses (A6.2)
- Choosing between HAL, LL and registers when you port between series (A17.1)

## Concept explanation

````layer beginner
### Arm designs the core, ST builds the chip

Arm doesn't make microcontrollers. It designs *processor cores* and licenses the design to chip makers. ST takes a Cortex-M4 core, wraps it with its own Flash, RAM, clocks, GPIO, timers and UARTs, and sells the result as an STM32F446. Every Cortex-M chip from any vendor shares the same core instructions and core peripherals, and differs in everything around it.

```callout analogy title="Analogy: an engine and the car around it"
The Cortex-M core is the **engine**: Arm designs it and many carmakers fit it. ST, NXP, Nordic and Microchip each build their own **car** around the engine: body, dashboard, fuel tank (Flash, RAM, peripherals). Two cars with the same engine accelerate the same way, but you can't swap the dashboards. That's why the CPU instructions, the interrupt controller and `SysTick` work identically on an STM32 and on an NXP part, while a GPIO register on one means nothing on the other.
```

### The ladder of cores

The names form a ladder from "small and frugal" to "fast and rich". All are 32-bit and all run Thumb instructions only:

| Core | Think of it as | Typical use |
|---|---|---|
| **Cortex-M0 / M0+** | The minimal core. Smallest, lowest power. No divide, no FPU | Sensor nodes, simple controllers, anything that runs on a coin cell |
| **Cortex-M3** | A full 32-bit workhorse with hardware divide | General-purpose control, older designs |
| **Cortex-M4 / M4F** | M3 plus DSP instructions, and with an **F** a single-precision FPU | Motor control, audio, sensors with maths: **our NUCLEO-F446RE** |
| **Cortex-M7** | A fast, deeper-pipeline M4 with caches | High-end control, graphics, fast signal processing |
| **Cortex-M33** | An M4-class core plus **TrustZone** security | Secure IoT devices |

STM32 families are named by letters and numbers: **F** (general purpose, "fast"), **L** (low power), **G** (a newer general purpose), **H** (high performance), **U** (ultra-low power) and **W** (wireless). The next widget shows which series uses which core; click the features you need and the series that lack them fade out:

```anim
core-family-explorer
```

The NUCLEO-F446RE carries an **STM32F446RE**: family F4, core **Cortex-M4F**, up to 180 MHz, 512 KiB of Flash, 128 KiB of SRAM. That is the chip the whole course uses.

### Why the compiler needs to know the core

A bigger core has more instructions. A program built for a Cortex-M4 contains instructions a Cortex-M0 cannot run, and the M0 would fault at the first one. So the compiler is told the target: `-mcpu=cortex-m4`. Later you'll see that, for the same C code, the target decides whether `a / b` is one instruction or a function call.
````

````layer intermediate
### Architecture, core, device: three different words

| Level | Example | Who defines it |
|---|---|---|
| **Architecture** (the instruction set and programmer's model) | ARMv7E-M | Arm |
| **Core** (one implementation of an architecture, with options) | Cortex-M4, revision r0p1 | Arm |
| **Device** (the chip) | STM32F446RE, silicon revision A | ST |

The architectures you'll meet:
- **ARMv6-M**: Cortex-M0, M0+ (and M1). A small subset of Thumb.
- **ARMv7-M**: Cortex-M3. Full Thumb-2, hardware divide.
- **ARMv7E-M**: Cortex-M4 and M7. ARMv7-M plus DSP/SIMD instructions and an optional FPU.
- **ARMv8-M Baseline** (Cortex-M23) and **ARMv8-M Mainline** (Cortex-M33, M55, M85): add the **TrustZone** security extension and more.

### Comparing the cores

From the Arm Technical Reference Manuals (the lab's `core_info.c` encodes this table, and the host program prints it):

| Core | Architecture | Pipeline | Max IRQ lines | HW divide | DSP | FPU option | Bit-band | TrustZone |
|---|---|---|---|---|---|---|---|---|
| Cortex-M0 | ARMv6-M | 3 | 32 | no | no | none | no | no |
| Cortex-M0+ | ARMv6-M | 2 | 32 | no | no | none | no | no |
| Cortex-M3 | ARMv7-M | 3 | 240 | yes | no | none | yes | no |
| Cortex-M4 | ARMv7E-M | 3 | 240 | yes | yes | single (FPv4-SP) | yes | no |
| Cortex-M7 | ARMv7E-M | 6 | 240 | yes | yes | single or double (FPv5) | no | no |
| Cortex-M33 | ARMv8-M Mainline | 3 | 480 | yes | yes (optional) | single (FPv5-SP) | no | yes (optional) |

Notes on the table:
- **"Optional"** matters: Arm sells *configurable* cores, and ST chooses the options. A Cortex-M4 **without** an FPU exists (it's called plain "M4"); the **F** says the FPU was included. The F446 has it.
- The M0+ has a shorter, 2-stage pipeline than the M0, so a taken branch costs fewer cycles; Arm positions it as the lower-power of the two.
- **Bit-banding** (single-bit alias regions, A0.2 and A1.4) exists on M3 and M4 but **not** on M7 or M33. Code that depends on it doesn't port from F4 to H7 or to a Cortex-M33 part.
- The **M7** adds caches and tightly-coupled memories on most parts. It is faster per MHz and is *not* a drop-in M4: timing changes (A1.5).

### Which STM32 has which core

Maximum CPU frequency is the family's top part; most devices are slower. Check ST's product selector for a real part.

| Series | Core | Max MHz | FPU | Notes |
|---|---|---|---|---|
| F0, C0, G0, L0 | M0 / M0+ | 32 to 64 | no | Entry level, lowest cost and power |
| F1, F2, L1 | M3 | 32 to 120 | no | The original "bluepill" generation (F1) |
| F3, G4 | M4F | 72 / 170 | yes | Analog-rich (G4 has fast ADCs, CORDIC, FMAC) |
| **F4** | **M4F** | **up to 180** | **yes** | **STM32F446RE: 180 MHz** |
| L4 | M4F | 80 | yes | Low power |
| F7 | M7 | 216 | yes (double on some parts) | Caches, TCM |
| H7 | M7 (some with an extra M4) | up to 480 | yes (double) | Highest performance |
| L5, U5, H5 | M33 | 110 / 160 / 250 | yes | TrustZone |

### Reading the identity from the chip

A0.4 read `SCB->CPUID` and decoded the part number. Now all five fields:

| Bits | Field | STM32F446 value | Meaning |
|---|---|---|---|
| [31:24] | Implementer | `0x41` | Arm |
| [23:20] | Variant | `0x0` | the "r" in r0p1 |
| [19:16] | Architecture | `0xF` | "read the ID registers" (ARMv7-M and ARMv8-M both report `0xF`; ARMv6-M reports `0xC`) |
| [15:4] | Part number | `0xC24` | Cortex-M4 (`0xC20` M0, `0xC60` M0+, `0xC23` M3, `0xC27` M7, `0xD21` M33) |
| [3:0] | Revision | `0x1` | the "p" in r0p1 |

`CPUID = 0x410FC241` is **Cortex-M4 r0p1**. That says what the *core* is. What the *chip* is comes from the other register, `DBGMCU->IDCODE` (`0xE004 2000`): `DEV_ID` `0x421` = STM32F446. Several STM32 families share one core (every F4 reads `0xC24`); you need `DEV_ID` to tell an F446 from an F411.

### Feature registers

The core also describes *itself*. Four registers cover what you need most:

| What | Register (address) | Field | Reads on an F446 |
|---|---|---|---|
| FPU present, precision | `MVFR0` (`0xE000EF40`) | single-precision [7:4] non-zero; double-precision [11:8] non-zero | `0x10110021`: single yes, double no |
| FPU enabled for code | `CPACR` (`0xE000ED88`) | CP10 [21:20] and CP11 [23:22] both `0b11` | `0x00F00000` after `SystemInit()`; `0` before |
| Hardware divide | `ID_ISAR0` (`0xE000ED60`) | Divide_instrs [27:24] non-zero | `0x01141110`: yes |
| Cycle counter, comparators | `DWT->CTRL` (`0xE0001000`) | `NOCYCCNT` bit 25 (0 = present), `NUMCOMP` [31:28] | `NUMCOMP` 4, counter present |
| MPU regions | `MPU->TYPE` (`0xE000ED90`) | `DREGION` [15:8] | 8 regions |

The "reads on an F446" column is what I expect for an M4F from the Cortex-M4 documentation (it was not read from a board for this lesson); the lab prints the real values from yours. The decoding works on any Cortex-M3/M4/M7.

### What ST decides: the vendor options

Because Arm's cores are configurable, ST's device header `stm32f446xx.h` records the choices:

```c
#define __CM4_REV                 0x0001U  /* core revision r0p1 */
#define __MPU_PRESENT             1U       /* STM32F4XX provides an MPU */
#define __NVIC_PRIO_BITS          4U       /* STM32F4XX uses 4 bits for the priority levels */
#define __FPU_PRESENT             1U       /* FPU present */
```

`__NVIC_PRIO_BITS = 4` is why the F446 has 16 interrupt priority levels, although the core allows up to 8 bits (A6.2). Another vendor's M4 may use 3 or 8. The CMSIS headers use these macros to compile the right code for the right chip.

### Choosing a core

Ask in this order:
1. **Does it need floating point in the hot path?** Yes: an M4F or better. No: an M0+ or M3 may do.
2. **Does it need 64-bit or DSP maths** (filters, FFT, motor control)? Yes: an M4 or M7 with DSP instructions.
3. **Does it need security isolation** (separate secure boot and application)? Yes: an M33.
4. **What is the power and cost budget?** An M0+ at a few tens of MHz wins on both.
5. **What do you already have?** Code, skills and boards for a family are worth a lot. The F4 is the best-supported general-purpose family.
````

````layer advanced
Four things follow:
1. **A missing instruction is not a compile error**, it's a library call. The M0 build of your control loop links and runs, and is just slower. Only a profiler (or the disassembly) tells you.
2. **The F446's FPU is single precision.** `double` arithmetic is software on the M4F, exactly as on an M3. Verified: with `-mfpu=fpv4-sp-d16`, `double + double` is still `bl __aeabi_dadd`.
3. **Cortex-M23 (ARMv8-M Baseline)** adds `SDIV`/`UDIV` over the M0 but still has no `UMULL` (verified: it calls `__aeabi_lmul` and `__clzsi2`, and divides with `sdiv`). It is "an M0+ with divide and TrustZone".
4. **Cortex-M33** with `-mfpu=fpv5-sp-d16 -mfloat-abi=hard` does `float` in hardware and `double` in software, like the M4F.

The toolchain keeps one pre-built C library per target. `arm-none-eabi-gcc ... -print-multi-directory` returns, verified: `thumb/v6-m/nofp` (M0/M0+), `thumb/v7-m/nofp` (M3), `thumb/v7e-m/nofp` (M4 soft float), `thumb/v7e-m+fp/hard` (**M4F: what CubeIDE selects for the F446**), `thumb/v7e-m+dp/hard` (M7 with a double FPU), `thumb/v8-m.main+fp/hard` (M33 with FPU). A project must link the library variant that matches its `-mcpu`/`-mfpu`/`-mfloat-abi` flags: A1.6 shows what happens if they disagree.

### The double-precision trap

On a single-precision FPU, one stray `double` makes a whole expression go through the library. Verified on the F446 target (`-mfpu=fpv4-sp-d16 -mfloat-abi=hard -O2`):

| C | Code |
|---|---|
| `y * 0.1` (`float y`) | `bl __aeabi_f2d` · `bl __aeabi_dmul` · `bl __aeabi_d2f`: convert up, multiply in software, convert back |
| `y * 0.1f` | `vmul.f32 s0, s0, s15`: one instruction |
| `sqrt(y)` (`float y`) | `bl __aeabi_f2d` · `bl sqrt` · `bl __aeabi_d2f` |
| `sqrtf(y)` | `vsqrt.f32` |

(`y * 0.5` is *not* affected at `-O2`: 0.5 is exactly representable as a float, so GCC folds it to a single-precision multiply. The trap hits constants that aren't exact, like 0.1.) GCC finds it for you: `-Wdouble-promotion` warns about *"implicit conversion from 'float' to 'double' to match other operand of binary expression"*, and `-Wconversion` (via `-Wfloat-conversion`) warns about *"conversion from 'double' to 'float' may change value"*. Both were silent in the code above only because the lab file silences them to build clean. Add `-Wdouble-promotion` to your flags. `-fsingle-precision-constant` turns bare constants into floats, but it doesn't fix `sqrt()`.

### M4 vs M7: not a drop-in upgrade

The same code, built for `-mcpu=cortex-m7`, runs on an M7, and faster. But four things change:
- **Timing is not portable.** The M7 has a 6-stage, partly dual-issue pipeline with branch prediction. Cycle counts measured with the DWT counter on an M4 (A3.5) don't transfer, and the order of instructions affects speed in ways it doesn't on an M4.
- **Caches.** Most M7 parts have instruction and data caches. DMA and the CPU can then disagree about memory (A12.5). The M4 has no data cache, so the problem doesn't exist on the F446.
- **No bit-banding** on the M7, and TCM regions instead.
- **Memory-system options** (ITCM, DTCM, AXI) decide where the stack and `.data` should be placed (A2.4).

### Thumb only, always

A Cortex-M has no ARM (32-bit) instruction state. Everything is Thumb or Thumb-2. A branch or an exception return to an address whose bit 0 is 0 would switch to the ARM state, which doesn't exist, and the core takes a UsageFault (`INVSTATE`). That is why every value in the vector table has its least-significant bit set (A2.2) and why `EXC_RETURN` values look the way they do (A6.4). It is also why `-mthumb` is in every flag set.

### What ARMv6-M cannot do

Beyond the table, a Cortex-M0/M0+ has a smaller register interface: only `PRIMASK` for masking (no `BASEPRI` or `FAULTMASK`), 4 priority levels (2 bits), most 16-bit Thumb instructions can only reach R0–R7, and there's no unaligned access. Code ported from an M3/M4 to an M0+ may be larger as well as slower, and RTOS ports differ (the FreeRTOS `CM0` port doesn't use `BASEPRI`).
````

### Identity registers at a glance

| Item | Address | Size | Owner | A0.4 / this lab reads |
|---|---|---|---|---|
| `SCB->CPUID` | `0xE000 ED00` | 32 | Arm | `0x410FC241` (core) |
| `FPU->MVFR0` | `0xE000 EF40` | 32 | Arm | FPU precision |
| `SCB->ISAR[0]` (`ID_ISAR0`) | `0xE000 ED60` | 32 | Arm | divide instructions |
| `MPU->TYPE` | `0xE000 ED90` | 32 | Arm | MPU regions |
| `DWT->CTRL` | `0xE000 1000` | 32 | Arm | cycle counter, comparators |
| `DBGMCU->IDCODE` | `0xE004 2000` | 32 | ST | `DEV_ID` `0x421` (device) |
| Flash size / UID | `0x1FFF 7A22` / `0x1FFF 7A10` | 16 / 96 | ST | A0.4 |

The `0xE000 xxxx` registers are the **Private Peripheral Bus**: part of the core and identical on every Cortex-M3/M4/M7, which is why the lab's pointer table works unchanged on a different vendor's M4. The `0xE004 xxxx` ones are ST's debug registers.

### Line-by-line: the non-obvious lines

| Line | Explanation |
|---|---|
| `(uint8_t)(cpuid >> CPUID_IMPLEMENTER_POS)` | Takes bits [31:24] and drops the rest. The cast is explicit (A0.1): the value is 0 to 255 by construction. |
| `((regs->mvfr0 >> MVFR0_SINGLE_POS) & NIBBLE_MASK) != 0U` | The standard field extract (A0.2): shift down, mask, compare. "Non-zero" is enough: the value says *which* FPU version, not just yes or no. |
| `(regs->cpacr & CPACR_CP10_CP11_MSK) == CPACR_CP10_CP11_FULL` | Both coprocessor fields must be `0b11`. Only CP10 enabled (`0x00300000`) is *not* an enabled FPU: the self-test checks it. |
| `(regs->dwtCtrl & DWT_CTRL_NOCYCCNT_MSK) == 0U` | `NOCYCCNT` is a "no" flag: 0 means the cycle counter exists. |
| `const volatile uint32_t *mvfr0;` in `FeatureSources` | A read-only register view (A0.4). On the host the same pointer points at a `const uint32_t`. |
| `.cpuid = (const volatile uint32_t *)0xE000ED00UL` | The only integer-to-pointer casts: in one macro, at the edge (A0.4). |
| `static const CoreSpec k_cores[]` | A `static const` table: private (A0.6), in Flash (`.rodata`), no RAM. |
| `check(strcmp(text, "Cortex-M4 r0p1") == 0, …)` | The self-test counts failures instead of stopping, so one run lists every broken check. |
| `make_cpuid(0x41U, 1U, 0xFU, 0xC27U, 1U)` | Builds a CPUID from its fields, to test the parser on a core you don't own (the M7 r1p1). |
| `CoreDebug->DEMCR \|= CoreDebug_DEMCR_TRCENA_Msk;` (`main.c`) | The DWT block answers only while `TRCENA` is 1. A debugger sets it, but a board running alone doesn't. Without this line `DWT->CTRL` may read 0 and the report would claim there is no cycle counter. |
| `__FPU_USED` | A compile-time constant from CMSIS: 1 if the *compiler flags* tell it to use the FPU, which is not the same as `__FPU_PRESENT` (the chip has one). |

## Common mistakes & debugging

### 1. Assuming `float` is hardware on every core
- **Symptom:** the code is correct but too slow after moving to another chip; the binary grew (the library routines are linked in).
- **Why:** an M0, M0+ or M3 (or an M4 built without `-mfpu`) does float maths in libgcc.
- **Diagnose:** `arm-none-eabi-objdump -d app.elf | grep __aeabi_f`, or the `.map` file.
- **Fix:** check `MVFR0`; compile with the flags that match the chip (A1.6).

### 2. A stray `double` on a single-precision FPU
- **Symptom:** a float expression costs far more than it should; `__aeabi_dmul` shows up in the profile.
- **Why:** `y * 0.1` and `sqrt(y)` use double constants and functions; the F446's FPU does float only (verified: `bl __aeabi_f2d` … `__aeabi_d2f`).
- **Fix:** `0.1f`, `sqrtf`, `sinf`; add `-Wdouble-promotion`.

### 3. FPU present but not enabled
- **Symptom:** a UsageFault (`CFSR.NOCP`) at the first floating-point instruction, or all-zero results.
- **Why:** `CPACR` resets to 0. `SystemInit()` must set CP10/CP11 to full access. A custom startup file that doesn't call it, or a bootloader that jumps without it, leaves the FPU off.
- **Diagnose:** the lab's `enabled:` line; read `SCB->CPACR`.
- **Fix:** `SCB->CPACR |= (3UL << 20) | (3UL << 22);` before `main()` (A2.3).

### 4. Wrong `-mcpu` or float ABI
- **Symptom:** a HardFault or UsageFault at the first instruction the core doesn't know (`INVSTATE`/`UNDEFINSTR`), or the linker reports *"uses VFP register arguments, … does not"*.
- **Why:** the object was built for a different core or float ABI than the code it's linked with.
- **Fix:** one set of flags for the whole project: for the F446, `-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard`.

### 5. Using the core ID to identify the chip
- **Symptom:** "all my boards report `0xC24`, so my firmware can't tell an F446 from an F411."
- **Why:** `CPUID` identifies the Cortex-M4; every F4 and G4 reports it.
- **Fix:** use `DBGMCU->IDCODE` (`DEV_ID`) and, for a factory serial, the 96-bit UID (A0.4).

### 6. Reading DWT without `TRCENA`
- **Symptom:** `DWT->CTRL` or `CYCCNT` reads 0 and never counts, even though the chip has the unit.
- **Why:** the DWT, ITM and TPIU blocks respond only while `DEMCR.TRCENA` is 1. A debugger sets it; a free-running board doesn't.
- **Fix:** set `CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk` first, then enable `CYCCNT` (A3.5).

### 7. Porting bit-banded code from an M4 to an M7 or M33
- **Symptom:** writes to the `0x4200 0000` alias region do nothing, or fault.
- **Why:** bit-banding exists on the M3 and M4, not on the M7 or the M33.
- **Fix:** use `BSRR`/set-reset registers or `LDREX`/`STREX` for atomic bit operations (A0.2, A5.3).

### 8. Trusting a core's cycle counts on another core
- **Symptom:** "this filter took 4,000 cycles on the F4, so it will take 4,000 on the H7."
- **Why:** pipeline depth, caches, branch prediction and memory timing differ.
- **Fix:** measure on the target, with the DWT counter, and say *which* chip (A1.5, A3.5).

### 9. Believing `__NVIC_PRIO_BITS` is a property of the core
- **Symptom:** priority code that works on an STM32F4 (4 bits) gives the wrong ordering on another vendor's M4.
- **Why:** the core supports 3 to 8 bits; the *vendor* decides (the F446: 4, so 16 levels).
- **Fix:** always use `__NVIC_PRIO_BITS` and the CMSIS `NVIC_SetPriority()` (A6.2).

### 10. Checking a series table from memory
- **Symptom:** a part chosen because "all F7s have a double-precision FPU" turns out not to.
- **Fix:** read the datasheet of the exact part number: FPU precision, MPU, caches and maximum frequency differ inside one series.

## Best practices & production tips

```callout production title="How professional teams choose and handle cores"
- **Write the core down in the project.** One header states `-mcpu`, FPU and float ABI, and the build breaks if the flags disagree with the chip: `static_assert(__FPU_PRESENT == __FPU_USED || !__FPU_PRESENT, …)` and a `#error` for unsupported cores.
- **Keep float code in `float`.** Suffix constants with `f`, call the `f` math functions, compile with `-Wdouble-promotion -Wconversion`. On a single-precision FPU, `double` should be a deliberate decision.
- **Detect, don't assume, in bring-up code.** Print `CPUID`, `IDCODE`, `MVFR0` and `CPACR` on the first power-up of a new board revision: it catches the wrong chip, a disabled FPU and a wrong clock early.
- **Be explicit about portability.** Put core-specific code (bit-band, DWT, FPU use, cache maintenance) behind a small layer and `#if __CORTEX_M == 4` / `__DCACHE_PRESENT` guards.
- **Port between series with a test, not a promise.** Run the same unit tests and a cycle-count benchmark on both targets before committing to a cost-down part.
- **Choose the family for the ecosystem as well as the core.** Tool support, errata history, long-term availability and the HAL/LL coverage matter as much as the pipeline depth.
- **Record the device revision** (`REV_ID`) in logs and field reports: the errata that apply depend on it (ST ES0298 for the F446).
```
